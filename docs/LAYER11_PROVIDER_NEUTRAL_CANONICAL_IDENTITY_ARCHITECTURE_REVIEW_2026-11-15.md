# Layer 11 — provider-neutral canonical identity architecture review

**Review date:** 15 November 2026  
**Status:** Architecture proposal only; no schema migration or identity approvals

## Purpose

Layer 11 needs a canonical football identity model that does not require Sportmonks to expose every competition, season, or team. Independent providers should be able to contribute evidence and, after explicit identity review, resolve to the same application-owned canonical entities.

The current intake catalogue is provider-independent as a review artefact. The persistence and promotion paths are not yet fully provider-neutral. This review records the gap and proposes a safe migration sequence. It does not authorize implementation or data writes.

## Verified current-state constraints

1. `football_repository.py` creates `football_leagues`, `football_seasons`, `football_teams`, `football_fixtures`, and `provider_entity_links`.
2. The league, season, and team rows each carry a required `source_provider`. Existing Sportmonks import paths use provider identifiers as the primary canonical row identifiers and create Sportmonks provider links.
3. `provider_entity_links` already separates a provider's entity identifier from a `canonical_entity_id`, and `provider_entity_link_approval_audit` records approval reasons. This is a useful foundation, but it does not by itself make the target entity IDs provider-neutral.
4. `docs/FREE_FIXTURE_CANONICAL_PROMOTION.md` currently requires competition, season and team links to existing Sportmonks entities, because the current prediction profile and enrichment workflow use Sportmonks IDs.
5. `provider_neutral_identity.py` currently generates review candidates for competitions and seasons only. Competition keys require name, country and competition type. Season keys require an existing canonical competition ID and a normalized label; provider season IDs are deliberately not accepted. There is no equivalent reviewed team-identity key in this module.
6. The provider-independent intake and Priority A evidence reviews explicitly prohibit automatic canonical creation and mapping approval. Provider agreement and fixture overlaps are evidence, not approval.

## Architecture decision proposed

Adopt application-owned canonical identifiers for competitions, seasons, teams and fixtures. Provider IDs remain source identifiers and are connected through explicit provider-entity links. Sportmonks becomes one provider among several, not the identity namespace or mandatory canonical authority.

This is a proposed target architecture, not a decision to create records now.

### Identity and provenance rules

- **Canonical IDs:** generated by the application and stable across provider changes. They must not encode or reuse a provider's numeric ID.
- **Provider IDs:** retain provider name, entity type, provider entity ID, first/last seen timestamps and raw-source provenance. Never compare IDs across providers as if they were globally unique.
- **Competition identity:** require verified name, country/territory and competition type. Also record gender, age scope, tier/division and reserve/senior scope where relevant. Ambiguous names and aliases require explicit reviewed aliases rather than fuzzy auto-merges.
- **Season identity:** belong to one canonical competition and retain source-specific season IDs. Validate season label, start/end boundaries, parent competition and authoritative schedule evidence independently. A shared calendar year or label alone is not sufficient.
- **Team identity:** require verified club/team identity and country/territory, with gender, age, reserve/first-team and other scope dimensions where applicable. Competition participation is supporting evidence, not the team's identity. Team-name changes and aliases must be versioned/reviewed.
- **Fixture identity:** resolve only after competition, season, home team and away team identities are established. Preserve each provider fixture ID separately. Exact kickoff and home/away orientation are required for automatic corroboration; material kickoff disagreements or reused IDs are held for review.
- **Approval:** every provider-to-canonical link must reference an existing canonical target and carry a non-empty approval reason, reviewer, timestamp and evidence reference. No automatic mapping approval.
- **Lifecycle:** identity merges/splits must be auditable and reversible. Never overwrite source observations or erase the old-to-new identity history.

## Proposed safe migration sequence

1. **Inventory and freeze assumptions.** Capture current row counts, provider-ID conventions, foreign-key relationships, all read/write call sites and the active Sportmonks-only promotion checks. Do not change production data.
2. **Specify canonical contracts.** Define canonical ID generation, required identity dimensions, source-link uniqueness, approval audit fields, alias/merge handling and conflict states. Add explicit schemas and tests before implementation.
3. **Additive schema design.** Prefer additive canonical identity tables and compatibility views/columns over re-keying existing tables in place. Existing Sportmonks-backed rows remain intact and are represented as one source's linked evidence. Do not run a migration until the full dependency inventory and rollback plan are reviewed.
4. **Read-only shadow reconciliation.** Build candidate crosswalks for existing rows and the strongest reviewed competitions (Premier League, Bundesliga and Scottish Premiership). Compare source rosters, parent competition/season relationships and fixture identities without persisting links.
5. **Dual-read validation.** Demonstrate that old Sportmonks-keyed reads and new application-owned canonical reads return the same verified records. Keep writes disabled during this phase.
6. **Explicit link approval.** Only after the evidence and shadow comparisons pass should a human approve specific competition, season and team links. Record the reason and evidence for each approval.
7. **Controlled provider-neutral writes.** Enable one bounded entity type at a time, beginning with competition/season metadata, then teams, then fixtures. Keep fixture promotion and predictions separately gated.
8. **Rollback and monitoring.** Retain source snapshots, migration checkpoints, row-count/integrity comparisons and a tested rollback path. Any unresolved identity conflict blocks promotion for that entity.

## Explicit non-goals for this review

- No CockroachDB connection or schema changes.
- No canonical competition, season, team or fixture rows created.
- No provider links or approval-audit rows created.
- No source observations, fixture data, statistics or prediction-ledger records changed.
- No provider enabled, no fixture route changed, and no prediction eligibility or model weights changed.
- No Sportmonks subscription or API scope changes.

## Open design questions before implementation

1. Should existing `football_leagues` / `football_seasons` / `football_teams` become compatibility views over new canonical tables, or should the repository introduce parallel `canonical_*` tables and migrate consumers gradually?
2. Which existing tables and prediction/data-collection paths still assume Sportmonks IDs directly, beyond the documented fixture-promotion gate?
3. What exact canonical team identity dimensions are mandatory for national teams, clubs, reserve teams and youth teams?
4. Should season identity use authoritative start/end dates as its primary discriminator, with a normalized label retained as descriptive metadata?
5. Which migration and rollback strategy preserves all existing IDs and foreign-key relationships without downtime or accidental relinking?

## Acceptance criteria for the architecture gate

- Canonical primary keys are demonstrably application-owned and provider-agnostic.
- Provider identifiers remain source-scoped and unique only within provider/entity type.
- Every link has a reviewable evidence trail and cannot silently retarget an existing source ID.
- Competition, season, team and fixture identity rules cover scope and conflict cases.
- Existing Sportmonks-backed data remains readable and unchanged during shadow migration.
- Tests prove that no fixture promotion, ingestion or prediction can bypass unresolved identity gates.
- A documented rollback plan and parity report exist before any production migration.

**Disposition:** provider-neutral canonical persistence is a genuine Layer 11 blocker. The next implementation task should be a repository-wide dependency inventory and schema design, not a live migration or automatic mapping.
